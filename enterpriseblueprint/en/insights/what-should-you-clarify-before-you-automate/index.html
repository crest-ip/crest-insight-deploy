When Finance corrects the same input again

Part 2 of 5

What should you clarify before you automate?

A recurring manual activity invites a natural question: can we automate it?

Sometimes the answer is yes. But if the activity compensates for an ambiguous input, a faster correction can make the underlying problem harder to see. A rule can correct a format, insert a default value or move an amount. To handle discrepancies reliably, you need to define which cases are errors, which are permitted exceptions and which require judgement.

The same empty field may have different causes

Consider a hypothetical case in which Finance completes missing project codes on supplier invoices. For some invoices, the code already exists on the purchase order. For others, the person who placed the order must decide which project should bear the cost.

Transferring an existing project code may reduce duplicate work. Filling every empty field with the same default value may instead conceal the fact that an allocation has not yet been decided. Before commissioning automation, distinguish between these cases and decide how exceptions should be handled.

Ask what the correction compensates for

Choose one activity you want to automate and describe it without system names. What comes in? What is expected to be true? Which control is performed? What changes? Who is accountable for the result?

These questions distinguish three situations:

  1. Reconstructed information. The information already exists but does not arrive in a usable form.
  2. Necessary control. The input needs to be verified before the next step.
  3. Genuine judgement. Someone must interpret a situation that cannot be resolved by a simple rule.

They may look equally manual in an activity list, but they should not be automated in the same way.

Do not merely move the correction

Detecting a discrepancy earlier is useful if the control moves to someone who has the information and can act. If it lands with someone who lacks the context, or in a system that merely stops the transaction, the problem may have changed location rather than been resolved.

Describe the entire handoff: sender, recipient, input, timing and accepted result. Only then can you decide whether a control should be removed, moved, simplified or retained.

Let the technology choice follow the question

Ask the vendor or internal team to demonstrate a specific scenario. Which input is used? What happens when the information does not agree? What is configured, what requires integration, and what still depends on a person?

Good automation does not begin with the annoyance of a manual activity. It begins with knowing which problem the activity handles, which control is still necessary and which result the next step must be able to trust.

Test the reasoning against an invoice case in which the goods-receipt evidence is missing.
